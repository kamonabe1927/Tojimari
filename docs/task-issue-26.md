## 1. 範囲の判断

マニフェストと今の段階の中に収まると判断した。

- 1.1（入っているソフト、古さ）の中の、spec-1.1.md の 2.4（今動いているかの印）の改修。新しい機能や出力の項目は足さない
- 読み取りだけで、VM の設定を変えない。外部へ送らない。新しい依存は入れない。使う外部コマンドも増えない（rpm の問い合わせは今の 1 回のまま）
- #14 で PM が決めた「Tojimari の親（`sudo`）は除かない」を、本人の依頼で変える。本人の言葉は PM の決定より優先する（manifest.md の優先の順）

## 2. 経緯

- 検証用 VM で `sudo python3 -B -m tojimari check` を実行すると、重点リストの `sudo` に「今動いている」の印が付いた（#26）
- 今の `processes.classify` は、Tojimari 自身（`self_pid`）とその子孫だけを印のもとから外し、親より上は見ない（task-issue-14.md の 3.1 の 3）。そのため、Tojimari を起動した `sudo` 自身が印のもとになっていた
- #14 では「その瞬間に実際に動いているので誤りではない」としたが、利用者が知りたいのは「Tojimari を動かす以外に sudo が動いているか」で、起動のたびに必ず付く印は誤解を生む（本人の判断）

## 3. 要件

### 3.1 外すプロセス

今まで外していたもの（Tojimari 自身とその子孫）に、次を足す。

1. Tojimari 自身（`self_pid`）から親（ppid）を上へたどり、いちばん近い `sudo` のプロセスを探す
2. 見つかったら、Tojimari の親からその `sudo` までの列を、すべて印のもとから外す
   - `sudo python3 -B -m tojimari check`（output-1.1.md の 1.1 の起動のしかた）では、外すのは親の `sudo` だけになる
   - `sudo` と Tojimari の間にほかのプロセスがある起動（`sudo sh -c '...'`、`sudo env ...`、`sudo -i` の後のシェルから起動など）では、間のプロセスも外す。本人の依頼の「それを起動した親のプロセスの列（sudo まで）」のとおりで、どれも Tojimari を起動するための列にあたるため
3. 2 で見つけた `sudo` の親も `sudo` なら、続くかぎり外す
   - `sudo` が端末（pty）を使うときなど、`sudo` が 2 段に重なるため。重ならない環境でも、続く `sudo` だけを外すので影響しない
4. 列のいちばん上の `sudo` より上（ログインのシェル、`sshd`、端末など）は外さない。祖先をまとめて外すと、ホストの `sshd` などの印まで消えるため（task-issue-14.md の 3.1 の 3 の理由はそのまま残る）
5. 親をたどっても `sudo` が見つからないとき（root のシェルから直接起動した、`sudo` を使わずに root なしで起動した、など）は、今までどおり Tojimari 自身とその子孫だけを外す。親やほかの祖先は外さない
   - 理由: `sudo` を経ずに起動したときに祖先を外す理由が無い。外すのは本人の依頼にある「sudo まで」の列に限る
6. ほかの端末やほかのセッションで動いている `sudo`（Tojimari の祖先でないもの）は、今までどおり印のもとにする（本人の依頼）

### 3.2 `sudo` の見分け方

- 祖先のプロセスの実行ファイルのパス（` (deleted)` を取り除いたもの。task-issue-14.md の 3.1 の 4 と同じ）を rpm の記録で引き、名前が `sudo` のパッケージの版が持つパスなら `sudo` とみなす
  - 理由: 印を付けるときと同じ rpm の記録で見分けるので、「重点リストの `sudo` に印が付くもと」とちょうど同じものを外せる。パスを Tojimari が決め打ちで持たずに済む
  - プロセス名（`/proc/<pid>/stat` の括弧の中）では見分けない。プロセス名は実行したものが自由に変えられ、実行ファイルとずれうるため
- 実行ファイルが読めない祖先（権限が無い、見回している間に終わった）は `sudo` とみなさず、そのまま上へたどる。root で動いていれば `sudo` の実行ファイルは読める。root なしで `sudo` が祖先にいる形（`sudo -u` でほかの利用者として起動したときなど）では `sudo` を見分けられないが、そのとき `sudo` は読めないプロセスとして数えられ、印のもとにはならないので、困らない
- rpm の問い合わせが失敗したとき（`checks.running_processes.status` が `unavailable`）は、印をそもそも付けないので、見分けは要らない（今の扱いのまま）
- 親のたどり方は今の `_descendants_of` と同じく、`/proc/<pid>/stat` の ppid を使い、ppid が 0 か見つからないところで止まる。輪になっていても止まること
- どの関数で見分けるか（`classify` に rpm の記録を渡すのか、外す pid を後から足すのか）はテックリードが決める

### 3.3 変わらないこと

- `tojimari check` と `--json` の出力の形（項目名、構造、終了コード）は変えない
- `checks.running_processes.unreadable` の数え方は変えない。3.1 で外したプロセスは、今の Tojimari 自身と同じく数に入れない（3.1 で外したものは実行ファイルを読めているはずで、数が変わることはほぼ無い）
- 注意の文言（`running_is_snapshot` を含む）は変えない
  - 理由: 今の文言の「印がないことを『使っていない』と扱わない」に、Tojimari を起動した `sudo` に印が付かないことも含まれる。表と JSON の注意を増やすと出力が長くなるだけで、読む側の判断は変わらない。外すものの説明は output-1.1.md の 2.8 に書く
- 違うルートディレクトリ、カーネルのスレッド、終わったプロセスなど、ほかの外し方は変えない

### 3.4 テストで確かめること

クラウド実行環境は AlmaLinux ではないので、今のテストと同じく架空の `/proc` の値と rpm の記録で確かめる（実機の生の情報は使わない）。

1. `sudo` → Tojimari の形で、親の `sudo` が印のもとにならず、重点リストの `sudo` の版の `running` が false になること（本人の「確かめてほしいこと」の 1）
2. 1 に加えて、Tojimari の祖先でない別の `sudo` のプロセスがあるとき、`sudo` の版の `running` が true になること（本人の「確かめてほしいこと」の 2）
3. `sudo` → `sudo` → Tojimari の形（2 段に重なる）で、どちらの `sudo` も外れること
4. `sudo` → シェル → Tojimari の形で、シェルと `sudo` が外れること
5. 列のいちばん上の `sudo` の親（シェルなど）と、その上（`sshd` にあたるもの）は外れないこと
6. `sudo` が祖先にいない形（シェル → Tojimari）で、シェルが外れないこと（今の「Tojimari の親は除かない」のテストは、この形に置き換える）
7. 祖先の `sudo` の実行ファイルが ` (deleted)` の付いたパスのときも、`sudo` とみなして外すこと
8. 実行ファイルが読めない祖先があるとき、それを `sudo` とみなさずに上へたどること
9. ppid が輪になっているとき、止まること
10. Tojimari 自身とその子孫を外すこと、`unreadable` の数え方など、今のテストの結果が変わらないこと
11. `check` を通した JSON で、1 と 2 の結果になること（今の `tests/test_check.py` の sudo を親に持つテストは、新しい決まりに合わせて直す）
12. リポジトリの最上位で `python3 -m unittest` がすべて通ること

## 5. やらないこと

- `sudo` 以外の権限を上げるコマンド（`su`、`pkexec`、`run0` など）で起動したときに、それを外すこと。本人の依頼は `sudo` だけで、範囲を広げない。`sudo` → `su` → シェル → Tojimari の形は、3.1 の 2 のとおり `sudo` までの列として外れる
- 注意の文言、JSON の項目、表の見た目を変えること
- 外したプロセスの数や名前を出すこと
- 印のもとの見分け方（ルートディレクトリ、サービスの判定、` (deleted)` の扱い）を変えること
- FastAPI の画面、1.2 以降
