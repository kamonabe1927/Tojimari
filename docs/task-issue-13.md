## 3. 要件

### 3.1 セキュリティ更新の件数と重要度

1. dnf が手元に持っているリポジトリ情報（キャッシュ）だけを使い、通信を起こさない（`--cacheonly`。#5、#12 と同じ）
   - 理由: Tojimari 自身は外へ通信せず、書き込みもしない決まり（output-1.1.md の 1.1、spec-1.1.md の 4）。リポジトリ情報を取り直すと、dnf が通信し、`/var/cache/dnf/` に書き込む
   - そのかわり、数は「dnf が最後にリポジトリ情報を取得した時点」のもので、最新とは限らない。そのことを必ず出力し（`security_updates_cache` の注意）、最新にしたいときは利用者が先に `sudo dnf makecache` を実行することを示す
2. 件数は「セキュリティ更新が出ている、入っているパッケージの名前の数」とする。勧告（RLSA などの番号）の数ではない
   - 理由: 勧告の番号を形を決めて取る方法が dnf 4 の `repoquery` に無いため（`updateinfo` の画面表示を読むことになる）。「どのソフトを確かめればよいか」という spec-1.1.md の 1 の目的には、名前の数のほうが直接こたえる
3. 重要度は、dnf の 4 つの段階（Critical、Important、Moderate、Low）と、どれにも当たらないもの（重要度が書かれていない勧告）に分ける。1 つの名前が複数の重要度に当たるときは、いちばん重いものにだけ数える（合計が名前の数と一致するように）
4. 名前ごとの一覧（名前と重要度）も出す。並びは重要度の重い順、同じ重要度の中では名前の文字列の昇順
5. リポジトリ情報が取れなかったとき（dnf が失敗した、キャッシュが無い、時間内に終わらないなど）は `unavailable` とし、「確認できなかった」と出す。「更新なし」「0 件」とは出さない（spec-1.1.md の 2.3）
   - 有効なリポジトリの一部のキャッシュが無いときに、dnf がそのリポジトリを黙って飛ばして「0 件」に見えることがないようにする（実行のときだけ dnf の `skip_if_unavailable` を無効にする指定を付けるなど。dnf の設定ファイルは変えない。方法はテックリードが決める）
   - 重要度ごとの問い合わせのどれか 1 つでも失敗したら、全体を `unavailable` にする（一部だけの数を出さない）
6. 0 件のときは `ok` で、件数 0 と出す（`unavailable` と区別する）

### 3.2 再起動待ちかどうか

1. 比べる対象は、rpm の記録にある `kernel` という名前のパッケージのうち、動いているカーネルと同じアーキテクチャの版
2. 動いているカーネル（`os.uname().release`）と `version-release.arch` が一致する版を、動いている版とする（#5 の `is_running_kernel` と同じ）
3. 1 の中で版がいちばん新しいもの（rpm の版の比べ方。epoch、version、release の順）が、動いている版より新しければ「再起動待ち」、そうでなければ「再起動待ちではない」
   - 版の比べ方は rpm の決まり（rpmvercmp）に合わせ、標準ライブラリだけで書く。`python3-rpm` などの rpm のライブラリは標準ライブラリでないので使わない（マニフェストの 4）
   - 入れた日時の新しさでは比べない（古い版を入れ直したときに取り違えるため）
4. 動いているカーネルが取れない、または 1 の中に一致する版が無いときは「確認できなかった」（`unknown`）とし、理由を出す。「再起動待ちではない」とは出さない
   - 例: `kernel-64k` など、`kernel` 以外の名前のカーネルで動いているとき。重点リストの `kernel` に合わせ、今回は `kernel` という名前だけを見る
5. ネットにつながっていなくても出る（rpm の記録と OS への問い合わせだけを使う）

### 3.3 最後に更新した日

1. dnf 履歴のデータベースを、#12 と同じ開き方（読み取り専用、確かめに通らなければ捨てる）で読む。開く処理は #12 のものを使い回す
2. 「更新した」は、パッケージの版を上げる処理（`trans_item.action` が libdnf の「upgrade」にあたる値）を 1 件以上含み、最後まで終わった（`trans.state` が libdnf の「done」にあたる値）処理とする
   - コマンド行（`trans.cmdline`）は読まない（利用者の打ったものそのままで、形を決められないため。dnf-automatic などの処理も拾えるようにするため）
   - `dnf install` のときに依存として版が上がったものも「更新した」に含める。「最後にパッケージの版が上がった日」という意味で出す
3. そのうちいちばん新しい処理の、終わった時刻（`trans.dt_end`。無いか 0 なら `trans.dt_begin`）を UTC で出す。あわせて、出力を作った時刻から何日たったか（切り捨て）を出す
4. 使う列が無い、開けない、問い合わせが失敗したときは「確認できなかった」（`unavailable`）とし、理由を出す
5. 履歴は読めたが当てはまる処理が 1 件も無いときは、「更新の記録が無い」（`none`）とする。「確認できなかった」とは区別する（インストールしてから一度も更新していない VM がこれにあたる）
6. ネットにつながっていなくても出る

### 3.4 書き込みをしない、通信しない

- Tojimari 自身は書き込みを一切しない（#5、#12 と同じ）。dnf 履歴のデータベースは #12 と同じく読み取り専用で開く
- dnf には `--cacheonly` を付け、リポジトリ情報を取り直させない
- 更新の適用、`dnf makecache` の実行はしない

### 3.5 root なしで実行したとき

- 見えた範囲だけを出す。それぞれ取れなければ 3.1 の 5、3.2 の 4、3.3 の 4 に従う
- `not_root` の注意は #5 のとおり出す

### 3.6 ほかの表示との関係

- 3 つのどれかが取れなくても、全体を失敗にしない（終了コードは 0。重点リストなどほかの表示は続ける）
- 今動いているかの印（1.1-C、#14）は今回作らない

### 3.7 テスト

- 標準の `unittest` だけを使い、リポジトリの最上位で `python3 -m unittest` を実行すれば全部通ること
- dnf の出力は `--queryformat` で決めた形で作った記録出力で、dnf 履歴は一時的な SQLite のデータベースで確かめる。中身は架空のものにし、実機の生の情報を入れない。テーブルと列の名前は #10 で本人が貼った構造に合わせる
- 少なくとも次を確かめる
  - セキュリティ更新: 重要度ごとの数え分け、1 つの名前が複数の重要度に当たるとき（重いほうにだけ数える）、重要度の無いもの、0 件（`ok`）、dnf の失敗（どの問い合わせの失敗でも `unavailable`、注意が出て、ほかの表示は続く）
  - 再起動待ち: 新しい版がある（`pending`）、動いている版がいちばん新しい（`not_pending`）、動いている版が rpm の記録に無い・取れない（`unknown`）、アーキテクチャの違う版は比べない、rpm の版の比べ方（数字と英字の混ざり、桁数の違い、`~`、`^`、epoch）
  - 最後に更新した日: upgrade を含む処理のうち最新のもの、終わっていない処理は数えない、upgrade を含まない処理だけのとき（`none`）、列が無い・開けないとき（`unavailable`）、`dt_end` が無いとき
  - JSON の構造と項目名が output-1.1.md の 2.7 のとおりであること。表に JSON と同じ中身が出ること
- コマンドを実行する部分と、データベースを開く部分は、テストで差し替えられるようにする（rpm、dnf を実際に呼ばない。実機の `/var/lib/dnf/history.sqlite` を開かない）

## 6. #13 の本文から変えたこと

- #13 の終わりの条件は、ネットにつながっていないときに「1 が『確認できなかった』になる」としていた。3.1 の 1 で通信を起こさない（`--cacheonly`）ことにしたので、ネットにつながっていなくても、dnf が前に取得したリポジトリ情報があれば 1 は出る。そのかわり、その数が最後に取得した時点のものであることを必ず出す
- 「確認できなかった」になるのは、リポジトリ情報（キャッシュ）が無いとき、dnf が失敗したときとする
- 理由: リポジトリ情報を取り直すと、Tojimari が dnf を通して外へ通信し、`/var/cache/dnf/` に書き込むことになる。これは #5 で決めた「Tojimari 自身は書き込みを一切しない」「外部への送信は行わない」（spec-1.1.md の 4）に反する。取り直すかどうかは利用者が `sudo dnf makecache` で決められる
- 本人が「実行のたびに取り直してほしい」と考える場合は、新しい issue で知らせてもらえば見直す

## 7. 実機での確認の手順（PR に書く内容の元）

本人が検証用 VM（AlmaLinux 10.2）のリポジトリの最上位で実行する。実装の結果に合わせて、セキュリティ担当が PR を作るときに整える。
実機の出力を issue や PR に貼るときは、ホスト名などを置き換えてから貼る（禁止事項 7）。

| 手順 | コマンド | 正しいときの表示 |
|---|---|---|
| 1 | `sudo dnf makecache`（ネットにつながった状態で。本人の判断で行う準備で、Tojimari は実行しない） | リポジトリ情報が取得される |
| 2 | `sudo python3 -B -m tojimari check` | `[古さ]` の表に、セキュリティ更新の件数と重要度、再起動待ちかどうか、最後に更新した日が出る |
| 3 | `sudo dnf updateinfo list --security --cacheonly` | 2 のセキュリティ更新の名前と重要度が、この一覧のパッケージ（名前の部分）と重要度に合っている。違いがあれば、多いもの・足りないものの名前を教えてほしい |
| 4 | 実装が使う `dnf repoquery` の呼び方そのもの（`--security`、`--sec-severity`、`--queryformat` を含む） | `--sec-severity` を変えると結果が変わり、`--security` を外すとセキュリティ以外の更新も出る（絞り込みが効いている） |

| 6 | `sudo dnf history list` | 2 の最後に更新した日が、Action(s) に Upgrade（または U）を含むいちばん新しい行の日時に合っている（`dnf history list` は現地時刻、Tojimari は UTC で出す） |
| 7 | 履歴の値の意味の確かめ（数だけを出す。中身は出ない）: `sudo python3 -B -c "import sqlite3; c=sqlite3.connect('file:/var/lib/dnf/history.sqlite?mode=ro&immutable=1', uri=True); print(c.execute('select action, count(*) from trans_item group by action').fetchall()); print(c.execute('select state, count(*) from trans group by state').fetchall())"` | 数の組が出る。6 の `dnf history list` の行の数と見比べる材料にする |

## 8. テックリードへの申し送り

- ファイルとモジュールの分け方、関数の分担、SQL の書き方は、テックリードが決めて `docs/` に書く。#12 の分け方（`runner.py` が実行とデータベースを開く処理、`packages.py`・`history.py` が問い合わせの形と読み取り）に合わせることを想定している
- JSON と表の形は output-1.1.md の 2.7 と 3.4、注意は 2.4 に決めた。変える必要があれば、設計に進む前に PM への差し戻しとして返す
- `trans_item.action`、`trans.state`、`trans_item.state` の値（libdnf の決まり）は、設計の文書に、どの値を何として使ったかと、確かめきれていないこと（実機確認の 6、7）を書く
- `--sec-severity` の 4 つの値の書き方（大文字小文字）、`--security` と `--upgrades` を組み合わせたときの意味、`skip_if_unavailable` を無効にする指定の付け方は、手元で確かめられない。決めた理由と、実機確認で確かめる点を書く
- dnf を重要度ごとに呼ぶと実行の回数が増える。時間の上限（`DNF_TIMEOUT`）の扱いと、全体の実行時間の見込みも書いてほしい
- 履歴のデータベースは、#12（後から入れたもの）と今回とで 2 回開くことになりうる。1 回にまとめるかどうかはテックリードが決めてよい。まとめる場合も、#12 の判定の結果と出力は変えない
- rpm の版の比べ方は、標準ライブラリだけで書く（3.2 の 3）。テストに、rpm の決まりで答えが分かっている組を入れる
