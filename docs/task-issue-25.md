## 2. 経緯

- dnf も PackageKit も動いていなかった。データベースは WAL 方式（`PRAGMA journal_mode` が `wal`）で、`/var/lib/dnf/` に `history.sqlite`、`-shm`、`-wal` があり、`-wal` には最後の update と同じ時刻の記録が残っていた
- 今の `runner.read_history_db` は `-journal` か `-wal` に中身があると開かずに `busy` とし、開くときも `mode=ro&immutable=1` で `-wal` を見ない。WAL 方式では dnf が動いていなくても `-wal` が残るので、いつも代わりの判定になる。判定をゆるめるだけでは `-wal` の中の記録（最近の処理）を見落とす

## 3. 要件

### 3.1 WAL 方式のときの読み方（本人の決定、#25）

1. データベースが WAL 方式のときは、読み取り専用（`mode=ro`）で、`immutable` を付けずに開く。dnf と同じ正規の読み方で、`-wal` の中の記録も含めて読む
2. `-wal` に中身があることだけを理由に止めない（`busy` にしない）
3. 書きかけかどうかは、今ある「読む前と後でデータベースの様子が変わっていないか」の確かめで見分ける。変わっていれば今までどおり `changed` とし、読んだ結果を捨てて代わりの判定にする。WAL 方式では最近の書き込みは `-wal` に入るので、様子には `-wal` の変化も入れる（何を様子に入れるかはテックリードが決める）
4. `-shm` が無いときは開かない（開くと SQLite が `-shm` を新しく作るため）。代わりの判定を使い、その理由を `history_fallback` の注意に出す。理由の文言は、「dnf が動いている途中」とは読めない、`-shm` が無かったことが分かるものにする（文言はテックリードが決める）
5. 開いたことで、`/var/lib/dnf/` に新しいファイルが作られないこと。`-shm` があり `-wal` が無いときなど、`-shm` 以外の補助ファイルが無いときに SQLite が何かを作るかは、テックリードが手元で確かめ、作るなら開かずに代わりの判定にする
6. 既にある `-shm` に SQLite が触れる（中身が書き換わりうる）ことは受け入れる。履歴の中身（本体と `-wal`）は書き換えない。書き込みの SQL は今までどおり失敗すること
7. 読み終わったら必ず閉じる（今までどおり）

### 3.2 WAL 方式でないとき

- WAL 方式でない（ロールバックジャーナルの方式で、`-journal` が残っている）ときの扱いは、テックリードが設計で決めて、理由とともに docs に書く（#25 の「確かめてほしいこと」）
- PM の考え: ロールバックジャーナルの方式で `-journal` に中身があるのは、書いている途中か、途中で止まった処理の巻き戻しが済んでいないときで、読み取り専用では巻き戻せず正しく読めない。今の `busy` のまま止める方向を想定する。WAL でない方式で `-journal` が無い・空のときは、今の `mode=ro&immutable=1` の読み方のままでよい
- WAL 方式かどうかの見分け方（データベースの先頭のヘッダを読む、など。今の様子の確かめで先頭 100 バイトはすでに読んでいる）は、テックリードが決める。データベースを開かずに見分けられる方法を優先する

### 3.3 変わらないこと

- 読み取り部（`history.py` の SQL と行の読み取り）、履歴が取れたときの判定（spec-1.1.md の 2.1）、最後に更新した日の取り方（2.3 の 3）は変えない
- 履歴が取れなかったときに代わりの判定にすること、その注意を出すことは変えない
- root なしで実行して読めないときは、今までどおり見えた範囲で代わりの判定になる（`permission` など）。`-shm` を開けないときの扱いもこの範囲で決める
- `tojimari check` と `--json` の出力の形（項目名、構造、終了コード）は変えない。増えるのは理由の文言の種類だけ

### 3.4 テストで確かめること

クラウド実行環境は AlmaLinux ではないので、一時ディレクトリに作ったデータベースで確かめる（実機の生の情報は使わない）。

1. WAL 方式で `-wal` に記録が残っていて `-shm` もあるとき、1 番の処理（`query_first_transaction`）と、最後に更新した日（`query_last_upgrade`）が取れること。最後に更新した日は、`-wal` の中にしかない処理の時刻が出ること（本体だけを読むと古い時刻になる作りにして確かめる）
2. 1 の読み取りの前後で、ディレクトリのファイルの一覧が変わらないこと。本体と `-wal` の中身が変わらないこと
3. WAL 方式で `-shm` が無いとき、開かずに代わりの判定になる理由の種類が返り、ファイルが作られないこと
4. 読んでいる間に本体か `-wal` が変わったとき、`changed` になること
5. WAL 方式でないときの扱い（3.2 で決めたもの）。`-journal` に中身があるときの結果と、無い・空のときに読めること
6. 3.1 の 5 で確かめた、補助ファイルが欠けているほかの組み合わせで、ファイルが作られないこと
7. 今あるテストのうち、開き方が `mode=ro&immutable=1` だけであることを前提にしたもの（`test_uri_has_both_options`、`-wal` に中身があると `busy` になる `test_busy` の WAL の部分など）は、新しい決まりに合わせて直す。直した理由を設計に書く
8. `check` と `cli` を通した表と JSON で、新しい理由が `history_fallback` の注意に出ること
9. リポジトリの最上位で `python3 -m unittest` がすべて通ること

テスト用のデータの作り方の手がかり: Python の `sqlite3` は、最後の接続を閉じると `-wal` を本体に書き戻して消す。`-wal` が残った状態は、書いた接続を開いたまま 3 つのファイルを別のディレクトリへ写すなどで作れる（作り方はテックリードが決める）。
