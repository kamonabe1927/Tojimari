## 2. 取り方の確かめ（#14 の「守ること」）

#10 の「Tojimari 側で形を決められる出力を使い、実機の形を推測で作らない」に照らして、次の取り方なら守れると判断した。止まって本人に聞く必要は無い。

| 知りたいこと | 取り方 | 形を決められる理由 |
|---|---|---|
| 動いているプロセスの一覧 | `/proc` の下の数字だけの名前のディレクトリ | Linux カーネルの決まった作り。コマンドの画面表示ではない |
| プロセスの実行ファイル | `/proc/<pid>/exe` のリンク先（`os.readlink`） | 値は実行ファイルの絶対パスそのもの。消されたファイルのときに末尾に ` (deleted)` が付くことだけがカーネルの決まり |
| 実行ファイルを持つパッケージ | `rpm -qf --queryformat`（または `rpm -qa --queryformat` のファイル一覧）。どちらにするかはテックリードが決める | `--queryformat` で出す列を Tojimari が決める（#5 と同じ） |
| systemd のサービスとして動いているか | `/proc/<pid>/cgroup` の cgroup v2 の行（`0::<パス>`） | カーネルの文書で決まった形。systemd は、サービスのプロセスを `<名前>.service` の cgroup に入れる。AlmaLinux 10 は cgroup v2 だけを使う |
| Docker コンテナの中のプロセスか | `os.stat("/proc/<pid>/root")` の `st_dev` と `st_ino` を、`os.stat("/")` と比べる | `/proc/<pid>/root` はそのプロセスのルートディレクトリを指すカーネルの決まった作り。中身は解釈せず、同じディレクトリかどうかだけを見る |

採らなかった取り方:

- `ps` の画面表示を読む: 列の形は指定できるが、`/proc` を直接読めば外部コマンドが要らず、プロセスごとに取れなかった理由（権限が無い、もう終わった）も分けられる
- `systemctl list-units` の画面表示を読む: 人が読む表示で形が決まっていない。また、どのプロセスがどのサービスのものかは分からない
- `systemctl show --property=MainPID,ControlGroup` を全サービスに対して呼ぶ: 形（`キー=値`）は決まっているが、サービスの数だけ呼ぶか全部を一度に聞く必要があり、`/proc/<pid>/cgroup` を読むより遅く複雑になる
- マウントの名前空間（`/proc/<pid>/ns/mnt`）を Tojimari 自身のものと比べる: 最初はこれにしたが、テックリードの差し戻しで改めた（2026-11-22）。systemd の `PrivateTmp=`、`ProtectSystem=`、`ProtectHome=`、`PrivateDevices=` などのあるホストのサービスは、ホストと同じファイルを動かしていても別のマウントの名前空間で動く。これで外すと、後から入れたサービスに印が付かず、spec-1.1.md の 2.4 の中心の要件に反する。コンテナや chroot はルートディレクトリが別になるので、ルートの比べ合わせなら、ホストのサービスを残してコンテナの中だけを外せる

手元（クラウド実行環境）には AlmaLinux も rpm の記録も無いため、次は実機確認（7）で本人に確かめてもらう。

- sshd などのサービスのプロセスの `/proc/<pid>/cgroup` が `0::/system.slice/<名前>.service` の形になっていること
- `rpm -qf` が、実行ファイルのパスから期待するパッケージ（例: `/usr/sbin/sshd` から `openssh-server`）を返すこと

## 3. 要件

### 3.1 「今動いている」の印（`running`）

1. `/proc` の下のプロセスを 1 回だけ見回し、それぞれの実行ファイルのパスを取る
2. 実行ファイルを持つパッケージを rpm の記録で調べ、そのパッケージの版（名前、epoch、version、release、arch が一致するもの）に「今動いている」の印を付ける
   - 印を付ける先は、重点リスト（`checks.focus_packages`）と後から入れたもの（`checks.user_installed`）の版の要素（output-1.1.md の 2.3）
   - 1 つのパスを複数の版が持っているとき（x86_64 と i686 の両方が入った glibc など）は、rpm が返したすべての版に印を付ける
3. 次のプロセスは結びつけない（印のもとにしない）
   - 実行ファイルが無いもの（カーネルのスレッドなど）、見回しているあいだに終わったもの
   - Tojimari 自身とその子プロセス（`rpm` など）。Tojimari を動かしている `python3` に印が付くと、「今動いている」の意味がぶれるため
   - Tojimari と違うルートディレクトリで動いているもの（Docker コンテナの中、chroot の中など）。パスがコンテナの中のものなので、ホストのパッケージに結びつけると誤るため（spec-1.1.md の 3「Docker コンテナの中身は表示しない」）
     - 見分け方: `os.stat("/proc/<pid>/root")` の `st_dev` と `st_ino` が、`os.stat("/")` と同じなら結びつけ、違えば結びつけない
     - マウントの名前空間が違うだけのもの（`PrivateTmp=` などのある systemd のサービス）は、ルートが同じなので結びつける
     - ルートが権限で読めないプロセスは結びつけず、読めなかった数（3.3 の 3）に数える
   - Tojimari の親や祖先（`sudo`、ログインのシェルなど）は除かない。要件の「Tojimari 自身とその子プロセス」に当たらず、祖先をまとめて除くとホストの `sshd` などまで外れるため。そのため `sudo` で実行すると、重点リストの `sudo` には「今動いている」の印が付く。実際にその瞬間に動いているので誤りではなく、output-1.1.md の 2.8 にそのことを書く
     - #26 で変えた（2026-11-27、本人の依頼）: Tojimari を起動した `sudo` までの親の列は結びつけない。それより上の祖先を除かないことは変わらない。[task-issue-26.md](task-issue-26.md) の 3.1
4. 実行ファイルのパスの末尾に ` (deleted)` が付いているとき（更新で入れ替わった古い実行ファイルが動いているとき）は、その印を取り除いたパスで調べ、今そのパスを持つパッケージの版に印を付ける
   - 理由: 更新した後に再起動していないサービス（sshd など）は、まさに確かめたい対象で、印が消えると「動いていない」ように見えてしまうため
   - そのため「今動いている」は「その版の実行ファイルのパスで動いているプロセスがある」という意味で、動いているのが更新前の中身である場合も含む。このことは output-1.1.md の 2.8 に書く。更新前の中身かどうかを見分けて出すことは今回はしない（spec-1.1.md の 2.4 の外）
5. kernel の版には、ここでの印は付かない（カーネルはプロセスの実行ファイルではないため）。動いているカーネルは、これまでどおり `is_running_kernel` で出す

### 3.2 「systemd のサービス」の印（`systemd_service`）

1. 3.1 で結びつけたプロセスのうち、システムのサービス（systemd がシステム側で起動したサービス）として動いているものがあれば、その版に「systemd のサービス」の印を付ける
2. 見分け方: `/proc/<pid>/cgroup` の cgroup v2 の行のパスを `/` で分けた部分のどれかが `.service` で終わり、かつパスが `/user.slice` の下ではないもの
   - 最後の部分だけを見ると、`Delegate=yes` のサービスが自分で作る子の cgroup（`/system.slice/<名前>.service/<子>`）で動くプロセスを外してしまうため（テックリードの差し戻し、2026-11-22）
   - 利用者のログインのセッション（`session-*.scope`）、利用者ごとの systemd（`user@*.service` とその下）は含めない。「サービスとして常駐しているか」を知りたいので、ログインして手で動かしたものはサービスに数えない
   - 細かな判定（`/user.slice` 以外にある利用者ごとのものの扱いなど）はテックリードが決めて、設計の文書に理由を書く
3. `systemd_service` が真なら、`running` も真になる（サービスの印は「今動いている」の一種）
4. cgroup が読めないプロセスは、`running` の印のもとにはするが、`systemd_service` の印のもとにはしない

### 3.3 見回し全体の結果（`checks.running_processes`）

印の意味を読む側が誤らないよう、見回しの結果を別に出す（形は output-1.1.md の 2.8）。

1. `/proc` を見回せた、かつ rpm への問い合わせが成功したときは `ok`
2. `/proc` を見回せない、または rpm への問い合わせが失敗したときは `unavailable` とし、理由を出す。このとき各版の `running` と `systemd_service` は `null` にする（「動いていない」と区別する）
3. 権限が無くて実行ファイルを読めなかったプロセスの数を出す。1 つ以上あれば、印の無い版の中に実は動いているものがありうることを注意に出す（`running_partial`）
   - 実行ファイルが読めなかったものと、ルートディレクトリ（3.1 の 3）が読めなかったものの両方を数える
   - root なしで実行すると、ほかの利用者のプロセスは読めないのでここに数えられる（spec-1.1.md の 3「見えた範囲だけを表示し、その旨を表示する」）
   - 見回しているあいだに終わったもの、カーネルのスレッド、3.1 の 3 で除いたものはこの数に入れない
4. ほかの確認（重点リスト、後から入れたもの、古さ）は、見回しが失敗しても続ける。終了コードは 0（#13 の 3.6 と同じ考え方）

### 3.4 注意の文言（`running_is_snapshot`）

今の文言（「今動いている」はその瞬間の様子。印がないことを「使っていない」と扱わない）は残し、次を足す。印が付かない理由が今回の作りで増えるため。

- Docker コンテナの中で動いているものには印を付けない
- 印は実行ファイルのパスで付けるので、更新した後に再起動していないプロセスは、新しい版の印として出る

### 3.5 書き込みをしない、通信しない

- Tojimari 自身は書き込みを一切しない（#5、#12、#13 と同じ）。`/proc` は読むだけ
- プロセスにシグナルを送らない。サービスを始めない・止めない

### 3.6 テスト

- 標準の `unittest` だけを使い、リポジトリの最上位で `python3 -m unittest` を実行すれば全部通ること
- `/proc` を読む部分と、rpm を呼ぶ部分は、テストで差し替えられるようにする（実機の `/proc` を前提にしない。rpm を実際に呼ばない）。差し替えに使う値は架空のもの（パス、pid、cgroup のパス）にし、実機の生の情報を入れない
- 少なくとも次を確かめる
  - 実行ファイルからパッケージの版への結びつけ、複数の版が同じパスを持つとき（両方に印）、どのパッケージも持たないパス
  - `systemd_service`: システムのサービス、`Delegate=yes` の子の cgroup（`/system.slice/<名前>.service/<子>`）、利用者のセッション、`user@*.service` の下、cgroup が読めないとき
  - 除くもの: 実行ファイルの無いもの、終わったもの、Tojimari 自身、違うルートディレクトリ（`st_dev` か `st_ino` が違う）
  - 除かないもの: マウントの名前空間だけが違う（ルートが同じ）プロセス、Tojimari の親（`sudo`）（#26 で変えた。親の `sudo` は除く。[task-issue-26.md](task-issue-26.md) の 3.4）
  - ルートディレクトリが読めないプロセス（結びつけず、`unreadable` に数える）
  - ` (deleted)` の付いたパス
  - 権限が無くて読めないプロセスがあるとき（数と `running_partial` の注意）
  - 見回しや rpm が失敗したとき（`unavailable`、各版の印が `null`、注意が出て、ほかの表示は続く）
  - JSON の構造と項目名が output-1.1.md の 2.3・2.8 のとおりであること。表に JSON と同じ中身が出ること（3.5）
- 既存のテストは、印の項目が足されたこと以外の結果を変えない

## 7. 実機での確認の手順（PR に書く内容の元）

本人が検証用 VM（AlmaLinux 10.2）のリポジトリの最上位で実行する。実装の結果に合わせて、セキュリティ担当が PR を作るときに整える。

- 5a で選んだサービスのパッケージが重点リストにも後から入れたものにも無いときは、表で確かめられない。テックリードが、確かめ方（後から入れたサービスで見るなど）を決めて手順を整える

## 8. テックリードへの申し送り

- ファイルとモジュールの分け方、関数の分担は、テックリードが決めて `docs/` に書く。#12・#13 の分け方（`runner.py` が実行と読み取り、ほかが形の決まった値の解釈）に合わせ、`/proc` を読む処理も `runner.py` の側に置いて差し替えられるようにすることを想定している
- JSON と表の形は output-1.1.md の 2.3・2.8 と 3.5、注意は 2.4 に決めた。変える必要があれば、設計に進む前に PM への差し戻しとして返す
- 実行ファイルからパッケージを引く方法（`rpm -qf` をパスごとに呼ぶ、まとめて呼ぶ、`rpm -qa` のファイル一覧から引く）は、テックリードが決める。決めるときに次を考える
  - `rpm -qf` は、どのパッケージも持たないパスについて、標準出力に文を出して終了コードを 0 以外にする。複数のパスを一度に聞くときに、出力のどの行がどのパスの答えかを取り違えないこと
  - spec-1.1.md の 2.4 は `rpm -qf` と書いている。`rpm -qa` のファイル一覧に変える場合は、理由を設計の文書に書き、spec-1.1.md の 2.4 の書き方もあわせて直す
  - 時間の上限（`RPM_TIMEOUT`）の範囲で終わるか、全体の実行時間の見込み
- Tojimari 自身の除き方（自分の pid と子プロセスの見分け方）は、テックリードが決める
- 実行ファイルのパスは、表にも JSON にも出さない（パス名に利用者の名前などが入りうるため。禁止事項 7 の考え方）。出すのはパッケージの版への印と、読めなかった数だけ
