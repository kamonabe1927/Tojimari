## 3. 要件

### 3.1 後から入れたものの判定（履歴が取れるとき）

1. `dnf repoquery --userinstalled` で、利用者が入れたと dnf が記録しているパッケージの一覧を取る（`--queryformat` で形を決める。通信を起こさないよう `--cacheonly` を付ける。issue #5 の `from_repo` の取り方と同じ考え方）
2. dnf 履歴の 1 番（`trans.id` が 1 の処理）に含まれたパッケージ名を、OS 標準の名前とみなす
   - `trans_item` の `trans_id` が 1 の行を、`item_id` で `rpm` に結びつけ、`rpm.name` を取る
   - 「1 番」は spec-1.1.md の 2.1 のとおり id が 1 の処理とする。いちばん小さい id など別の処理で代わりにしない（履歴が消されているときに、インストール時でない処理を OS 標準と取り違えないため）
3. 1 から、2 の名前を除いたものを「後から入れたもの」とする。名前だけで比べる（版、アーキテクチャは見ない）
   - 理由は requirements.md の「1.1 で決まったこと」のとおり。インストール後に更新した OS 標準（kernel など）を、名前で OS 標準に分類するため
   - 2 に入っている名前のパッケージを、利用者がいったん消して入れ直した場合も OS 標準に分類される。これは判定の決まりとして受け入れる
4. 重点リストとの重なりは除かない。重点リストは別枠で常に出すもので、後から入れたものの判定とは独立しているため（spec-1.1.md の 2.2）

### 3.2 履歴が取れないとき（代わりの判定）

次のどれかに当たるときは、履歴が取れなかったとみなす。

- `/var/lib/dnf/history.sqlite` が無い、読み取り専用で開けない（root なしで権限が足りないときを含む）
- 2 に挙げた列のどれかが無い
- `trans.id` が 1 の処理が無い、またはその処理に rpm のパッケージが 1 件も無い
- 問い合わせの途中で失敗した（壊れている、ロックされているなど）

このときは、3.1 の 1 の一覧のうち、入れた元のリポジトリ（`from_repo`）が `anaconda` のものを OS 標準とみなして除き、残りを「後から入れたもの」とする（spec-1.1.md の 2.1）。
出力には `history_fallback` の注意を出し、精度が落ちること（インストール後に更新した OS 標準が後から入れたものに混ざりうること）と、履歴が取れなかった理由の要約を書く。

### 3.3 後から入れたものの一覧そのものが取れないとき

`dnf repoquery --userinstalled` が失敗したときは、後から入れたものを判定できない。このときは「無かった」と出さず、「確認できなかった」と出す（`checks.user_installed.status` を `unavailable` にし、`user_installed_unavailable` の注意に理由の要約を出す）。重点リストなど、ほかの表示は続ける（全体を失敗にしない）。

### 3.4 表示する内容

- 各パッケージの版の要素は output-1.1.md の 2.3 の形（パッケージ名、epoch、version、release、arch、evr、入れた元のリポジトリ）
- 版の値は、重点リストと同じく rpm の記録（`rpm -qa` の一覧）から取る。dnf の出力は「どの名前が後から入れたものか」と「入れた元」の判定にだけ使う（重点リストと後から入れたものとで、同じパッケージの版の見え方がずれないようにするため）
- 同じ名前の版が複数あれば、すべて並べる
- 並びは名前、version、release、arch の文字列の昇順
- 今動いているかの印（1.1-C）と古さ（1.1-B）は今回作らない。置き場所だけ決まっていて（output-1.1.md の 2.5）、今回は空の値や仮の値を出さない

### 3.5 書き込みをしない

- Tojimari 自身は書き込みを一切しない（issue #5 と同じ）。dnf 履歴のデータベースも、読み取り専用で開く
- データベースを開いたことで、`/var/lib/dnf/` に新しいファイル（ジャーナルなど）が作られないようにする。作られうる開き方しかないと分かったときは、設計に進まずに PM へ差し戻す
- 開いたデータベースは、使い終わったら必ず閉じる

### 3.6 root なしで実行したとき

- 見えた範囲だけを出す。データベースを開けなければ 3.2 の代わりの判定に、`dnf repoquery` が失敗すれば 3.3 に従う
- `not_root` の注意は issue #5 のとおり出す

### 3.7 テスト

- 標準の `unittest` だけを使い、リポジトリの最上位で `python3 -m unittest` を実行すれば全部通ること
- dnf 履歴の読み取りは、テストの中で一時的な SQLite のデータベースを作って確かめる。テーブルと列の名前は、#10 で本人が貼った検証用 VM の構造に合わせる。中身（パッケージ名など）は架空のものにし、実機の生の情報を入れない
- `dnf repoquery --userinstalled` の出力は、`--queryformat` で決めた形で作った記録出力で確かめる
- 少なくとも次を確かめる
  - 履歴が取れるとき: 1 番に含まれた名前（更新後の kernel など、版が違うものを含む）が除かれ、残りが後から入れたものになる
  - 履歴が取れないとき（ファイルが無い、列が無い、`trans.id` が 1 の処理が無い、1 番に rpm が無い）: `from_repo` が `anaconda` のものが除かれ、`history_fallback` の注意が出る
  - `dnf repoquery --userinstalled` が失敗したとき: `status` が `unavailable` になり、`user_installed_unavailable` の注意が出て、重点リストは出る
  - 後から入れたものが 0 件のとき: 空の一覧で、`status` は `ok`（「確認できなかった」とは区別する）
  - 同じ名前の版が複数あるとき、epoch があるとき
  - JSON の構造と項目名が output-1.1.md のとおりであること。表に JSON と同じ中身が出ること
- コマンドを実行する部分と、データベースを開く部分は、テストで差し替えられるようにする（rpm、dnf を実際に呼ばない。実機の `/var/lib/dnf/history.sqlite` を開かない）

## 6. 実機での確認の手順（PR に書く内容の元）

本人が検証用 VM（AlmaLinux 10.2）のリポジトリの最上位で実行する。実装の結果に合わせて、セキュリティ担当が PR を作るときに整える。
実機の出力を issue や PR に貼るときは、ホスト名などを置き換えてから貼る（禁止事項 7）。

| 手順 | コマンド | 正しいときの表示 |
|---|---|---|
| 1 | `ls -a /var/lib/dnf/ > /tmp/before.txt` | （何も出ない。2 の前のファイルの名前を控える） |
| 2 | `sudo python3 -B -m tojimari check` | `[後から入れたもの]` の表が出る。履歴を使った判定なので、`[注意]` に履歴が取れなかった旨は出ない |
| 3 | `sudo python3 -B -m tojimari check --json \| python3 -c "import json,sys; d=json.load(sys.stdin)['checks']['user_installed']; print(d['status'], d['method']); print(sorted({p['name'] for p in d['packages']}))"` | `ok history` と、名前の一覧が出る。spec-1.1.md の 7 の 15 件（docker-ce、docker-ce-cli、containerd.io、k3s-selinux、epel-release、gh、htop、gcc、git、vim-enhanced、wireshark-cli、sysstat、dnf-automatic、openssl、tar）と見比べる。違いがあれば、多いもの・足りないものの名前を教えてほしい |
| 4 | `ls -a /var/lib/dnf/ \| diff /tmp/before.txt -` | 何も出ない（データベースを開いたことで新しいファイルができていない） |
| 5 | `python3 -B -m tojimari check`（sudo なし） | 表は出る。データベースを開けない場合は `[注意]` に、履歴が取れず代わりの判定を使った旨が出る。開ける場合は 2 と同じ一覧になる。どちらでも `not_root` の注意が出る |
| 6 | 実装が使う `dnf repoquery --userinstalled` の呼び方そのもの（`--queryformat` を含む） | 3 の一覧は、この出力から 1 番の名前を除いたものになっている |
| 7 | 3 をネットにつながっていない状態で実行する | 3 と同じ結果になる（`--cacheonly` で通信を起こさない） |
| 8 | `git status` | 実行のあとに、リポジトリに新しいファイル（`__pycache__` など）ができていない |

- 6 の呼び方は、実装で決まったものに置き換える
- 履歴の 1 番に含まれた件数だけを確かめたいときは、次で数だけを出せる（中身は出ない）。開き方は実装と同じ `mode=ro&immutable=1` にする（`mode=ro` だけで開くと `/var/lib/dnf/` にファイルが作られることがある。[design-issue-12.md](design-issue-12.md) の 2.2 と 9 の J）。`sudo python3 -B -c "import sqlite3; c=sqlite3.connect('file:/var/lib/dnf/history.sqlite?mode=ro&immutable=1', uri=True); print(c.execute('select count(distinct r.name) from trans_item t join rpm r on r.item_id=t.item_id where t.trans_id=1').fetchone()[0])"`

## 7. テックリードへの申し送り

- ファイルとモジュールの分け方、関数の分担、SQL の書き方は、テックリードが決めて `docs/` に書く。今の `packages.py`（読み取り）と `runner.py`（実行）の分け方に合わせ、データベースを開く部分を実行側に、取り出した行の扱いを読み取り側に置く形を想定している
- JSON と表の形は output-1.1.md の 2.6 と 3.3 に決めた。変える必要があれば、設計に進む前に PM への差し戻しとして返す
- 読み取り専用で開く方法（URI の `mode=ro`、`immutable=1` など）は、3.5 の「新しいファイルを作らない」と「dnf が同時に書いているときに壊れた中身を読まない」の両方を見て選び、理由を書いてほしい。手元で確かめきれない点は、実機確認の手順（6 の 4）で確かめる
- 列があるかの確かめ方（`PRAGMA table_info` など）も、Tojimari 側で形を決められる方法にする
- データベースのパスは `/var/lib/dnf/history.sqlite` に固定する（dnf の設定から読み取ることはしない。設定を読むと読み取る対象が増えるため。パスが違う VM では 3.2 の代わりの判定になる）
- `dnf repoquery --userinstalled` の `%{epoch}` は、epoch が無いとき `0` が出る想定で、issue #5 の `version_key` の扱いがそのまま使えるはず。確かめきれない点は実機確認の手順に入れる
- 3.1 の判定で、rpm の記録にあるのに dnf の一覧に無いもの、dnf の一覧にあるのに rpm の記録に無いものの扱いは、設計で決めてよい（どちらも「後から入れたもの」に入れない方向を想定）
