## 1. 目的と位置付け

- 個人用のローカル開発 VM（AlmaLinux）を、手間をかけずに固い状態から始められるようにする
- 対象は商用環境ではなく開発環境。開発環境を少しでも守れる土台を作る
- Tojimari 自体はセキュリティソフトではない。セキュリティ面の環境準備の補助であり、セキュリティを担保しない

## 2. 対象範囲

- 開発環境のみ（商用環境は対象外）
- OS は AlmaLinux のみ
- UTM、VMware Player などで起動するローカル VM のみ
- 個人利用のみ

## 3. やらないこと

- VPS や外部公開サーバ向けの機能を足さない
- AlmaLinux 以外のディストリビューションへの対応を足さない
- 複数人利用を前提にした機能（権限管理、マルチテナントなど）を足さない
- 商用環境向けの機能を足さない
- メール、Slack 通知など外部へ情報を送る機能を足さない（結果はログ、標準出力、FastAPI 画面のみ。外部送信は情報流出の経路になりうるため）
- FastAPI 画面の既定の待ち受けを localhost 以外にしない。外部に開くための FastAPI や firewall-cmd の設定を Tojimari が自動で行わない（利用者が設定する）
- セキュリティを担保する・保証すると読める表現を文書や出力に書かない

## 4. 技術の方針

- 一般的な知見の多い技術を採用する
- 実装言語は Python（AlmaLinux 標準の python3）に統一する
  - 情報の取得は標準ライブラリだけで行う
  - 画面は FastAPI で作る
  - シェルスクリプトは薄い起動用だけに使う
- 第3段階（差分の反映）の設定変更は Ansible（ansible-core）を使う。入れるのは第3段階に入ってからで、そのときに禁止事項5の確認を行う

理由:

- 実装言語や設定の仕組みが途中で変わると、作り直しの手間が大きすぎるため、委任の外に置く
- AlmaLinux 10 の dnf は Python で動くため、python3 は最初から入っている（検証用 VM での `rpm -q python3` による確認はまだ）。JSON の出力や表の整形も標準ライブラリでできる
- 1言語に揃えると、レビューとセキュリティ確認の範囲が揃う
- 画面に PHP などを使うと、守りたい VM に常駐するサービスや依存が増えるため使わない
- Ansible は Python 製で冪等に動き、VM の中で自分自身に対して実行すれば SSH も要らない。第2段階の「あるべき状態」の書き方を、第3段階でそのまま反映に使える形にそろえやすい。似た道具（pyinfra など）より知見が多い

## 5. 段階リリース

- 第1段階は現状チェック、第2段階はあるべき状態との差分抽出、第3段階は差分の反映
- 第1段階は 1.1（入っているソフト、古さ）→ 1.2（VM とホストの境目）→ 1.3（認証情報、外向き通信）の順に進める
- 今の段階より先の機能（例: 第1段階での変更適用）は先回りして作らない
