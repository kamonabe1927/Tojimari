## 1. 背景と課題

- 個人で使う開発サーバは、セキュリティ設定が甘かったり、ログが監視できていなかったりする可能性がある。
- お金をかけて守る仕組みを用意することはできない。
- 一番面倒に感じているのはキッティング。用途に応じてVMを使い分けたいとき、
  毎回最初から設定するのが面倒で「どうせ個人用だし、デフォルトでゆるくてもいいか」となる。
- 同種のOSSは世の中に多くあるが、既製品は使いこなせない機能が多い。
  自分が欲しい機能だけが、自分に使いやすい形で入っているものが欲しい。
- 商用環境は費用をかけてセキュリティを守ることが多い。一方、開発環境は使い捨ての感覚で扱われることもあり、
  商用環境に比べて堅牢でない可能性がある。

### 1.1 位置付け

- 対象は商用環境ではなく開発環境。
- Tojimari は、開発環境を少しでも守れる土台を作るためのもの。
- Tojimari 自体はセキュリティソフトではない。セキュリティ面の環境準備を補助するものであり、セキュリティを担保するものではない。

#### 1.1 で決まったこと（経緯と理由）

実装時の仕様は [spec-1.1.md](spec-1.1.md) にまとめた。ここには決めた経緯と理由を残す。

- 「後から入れたもの」の判定（2026-11-20）: dnf 履歴の1番（OS インストール時の処理、`@anaconda`）に含まれたパッケージ名を OS 標準とみなし、`dnf repoquery --userinstalled` からそれを除いたものを「後から入れたもの」とする
  - 理由: 入れた元のリポジトリ（`from_repo`）だけで判定すると、インストール後に更新した OS 標準（kernel など）が更新元のリポジトリに書き換わり、後から入れたものに混ざるため。名前で判定すれば更新しても変わらない
  - 履歴が取れない VM では `from_repo` が `anaconda` かで代わりに判定し、精度が落ちることを出力に明記する
  - 検証用 VM での見込み: docker-ce、gh、git、gcc、htop、wireshark-cli など15件が残り、kernel 系は OS 標準に分類される
  - 履歴の 1 番の取り方（2026-11-21、issue #10 で本人が案 B を選んだ）: dnf が履歴をしまっているデータベース `/var/lib/dnf/history.sqlite` を、標準ライブラリの `sqlite3` で読み取り専用で開き、SQL で必要な列（`trans.id`、`trans_item.trans_id`・`item_id`、`rpm.item_id`・`name`）だけを取り出す
    - 理由: `dnf history info 1` は人が読む画面表示で、Tojimari 側で形を決められない（実機の形を推測で読むことになる）。データベースなら取り出す形を SQL で決められ、新しい依存も要らない
    - 気をつけること: テーブルの構造は dnf の内部のもので、約束されたものではない。使う列が無いときや開けないときは、`from_repo` による代わりの判定に切り替えて、その旨を出す。構造は検証用 VM（AlmaLinux 10.2、dnf 4.20）で本人が確かめた（#10）
    - 採らなかった案: 画面表示を読む（形を推測することになる）、いつも `from_repo` で判定する・rpm の `INSTALLTID` で見分ける（どちらも更新した OS 標準が後から入れたものに混ざる）
    - WAL 方式の読み方（2026-11-27、issue #25 で本人が決めた）: 検証用 VM のデータベースは WAL 方式で、dnf が動いていなくても `-wal` が残り、最近の記録はその中にあった。`mode=ro&immutable=1` は `-wal` を見ず、`-wal` に中身があると止める作りでは、いつも代わりの判定になっていた。WAL 方式のときは、読み取り専用で `immutable` を付けずに開き（dnf と同じ正規の読み方）、`-wal` の中身も含めて読む。書きかけかどうかは読む前と後の様子の確かめで見分ける。`-shm` が無いときは SQLite が新しく作ってしまうので開かず、代わりの判定にする。既にある `-shm` に SQLite が触れることは受け入れる（新しいファイルは作らず、履歴の中身は書き換えない）。[task-issue-25.md](task-issue-25.md)
- 重点リスト（2026-11-20）: 上の判定とは別枠で常に表示する。Tojimari が小さな固定リストとして持つ
  - 選ぶ基準: 外から届く入口になる、権限昇格につながる、多くのソフトが使う土台になる、のいずれかに当たるもの
  - 中身: kernel（動いている版と入っている版の両方）、openssh-server、openssh、openssl-libs（openssl コマンドではなくライブラリ本体）、glibc、sudo、systemd、polkit
  - 利用者が設定で足し引きできるようにするかは、要望が出てから考える
  - セキュリティ更新の有無（`dnf updateinfo`）は重点リストとは別に、「古さ」の表示で使う想定
- 古さの表示（2026-11-20）: 次の3つを見せる
  1. セキュリティ更新の件数と重要度（`dnf updateinfo`）。取得できなかったときは「確認できなかった」と出し、「更新なし」とは出さない
  2. 再起動待ちかどうか（動いているカーネルが、入っている最新版より古くないか。`dnf needs-restarting -r` も使える）
  3. 最後に更新した日（dnf 履歴の最後の update / upgrade）
  - 理由: 「放置した VM が古くなる」に直接こたえるため。2 と 3 は手元の記録だけで出せるので、オフラインの VM でも空にならない
  - 取り方（2026-11-22、issue #13）: 1 は `dnf repoquery --cacheonly --upgrades --security`（重要度ごとに `--sec-severity`）を `--queryformat` 付きで使い、件数はパッケージの名前の数とする。2 は rpm の記録の `kernel` の版を rpm の決まりで比べる。3 は dnf の履歴のデータベース（#12 と同じ読み方）から、版を上げる項目を含み最後まで終わった処理の時刻を取る
    - 理由: どれも Tojimari 側で形を決められる取り方で、新しい依存も要らない。`dnf updateinfo` と `dnf history` の画面表示は形を決められないので読まない。`dnf needs-restarting -r` はプラグインが要り、カーネル以外の更新でも再起動待ちになるので使わない
    - リポジトリ情報を取り直さない理由: 取り直すと Tojimari が dnf を通して通信し、`/var/cache/dnf/` に書き込むことになり、「書き込みをしない」「外部への送信を行わない」に反するため。そのかわり、数が最後に取得した時点のものであることを必ず出し、最新にしたいときは利用者が `sudo dnf makecache` を先に実行する
- 使われているかの表示（2026-11-20）: 今動いているプロセスの実行ファイルを `rpm -qf` でパッケージに紐づけ、一覧に「今動いている」と印をつける。systemd のサービスかどうかも印にする
  - 理由: 「Java は入っているが使われているのか」という要望に最も近い形でこたえられるため。手で起動したものも拾える
  - 取り方（2026-11-22、issue #14）: プロセスの実行ファイルは `/proc/<pid>/exe`、サービスかどうかは `/proc/<pid>/cgroup` を標準ライブラリで読む。パッケージへの結びつけは rpm の `--queryformat` 付きの問い合わせで行う
    - 理由: どれも Tojimari 側で形を決められ（カーネルの決まった形か `--queryformat`）、新しい依存も要らない。`ps` や `systemctl list-units` の画面表示は読まない
    - Tojimari と違うルートディレクトリで動いているプロセス（Docker コンテナの中など）は結びつけない。パスがコンテナの中のもので、ホストのパッケージに結びつけると誤るため。マウントの名前空間で見分けると、`PrivateTmp=` などのある systemd のサービスまで外れるので、ルートディレクトリが同じかで見分ける（2026-11-22、テックリードの差し戻し）
    - 更新で入れ替わった古い実行ファイル（` (deleted)`）で動いているプロセスも、今そのパスを持つ版に印を付ける。更新した後に再起動していないサービスこそ確かめたい対象で、印が消えると動いていないように見えるため
  - `sudo` で実行する前提とする。root なしで実行したときは、見えた範囲だけを出し、その旨を表示する
  - その瞬間の様子なので「今動いていない＝使っていない」とは扱わず、出力にも明記する。Docker コンテナ内のプロセスは紐づかないため出ない
- 出力の形（2026-11-20）: 1.1 は標準出力のみ。人が読む表と JSON の両方を出せるようにする。FastAPI の画面は、その JSON を読んで表示する形で 1.1 のすぐ後に足す
  - 理由: 1.1 を小さく保ち、まず中身の正しさを確かめるため。JSON の形が先に決まれば、画面と標準出力で内容がずれない
- 検証用 VM で確認できた材料: dnf 4.20、`dnf updateinfo` でセキュリティ更新の有無が取れる（リポジトリ情報の取得が要るため、オフラインでは使えない）、カーネルは複数世代が入りうる（入っている版と動いている版のずれも古さの確認に使える）

## 3. たたき台（未確定）

ここは会話の中で出た案で、まだ合意したものではない。要件定義で見直す。

### 3.1 守るべきものの重心

ローカルVMでは外から攻められる入口がほぼないため、「中から外へ」と「VMからホストへ」を重く見る。

- 持ち込んだコードが悪さをする（パッケージ、試しに動かすOSS、AIエージェントが実行するコマンド）
- VM内に置いた認証情報が抜かれる（トークン、SSH鍵、APIキー）
- VMから自宅LANやホストへ届く（ブリッジ接続、ホストとの共有フォルダ）
- 放置したVMが古くなる（更新がたまる）

### 3.2 機能の候補

- 用途プロファイルを選ぶと、設定一式が入る
- 外向き通信の制限と記録
- ネットワーク接続方式と共有フォルダの点検、危ない組み合わせの警告
- 認証情報の置き方の決め打ち
- 何が実行されたかの記録、起動時の自動更新
- 指摘は絞って出し、直し方まで示す
- 「いつもと違うこと」だけをログに記録する（外部への通知はしない）
- 導入ソフトの棚卸し（できたらいいな程度の要望）
  - 脆弱性情報が出たときに、ソフトごとに確認コマンドを調べて打つ負担を減らす
  - 表示対象の方針（2026-11-19 本人の意向。機能自体を作るかは未確定）
    - 対象: OS 標準で入っていて、脆弱性が見つかることが比較的多いと判断したもの（カーネル、OpenSSH など）と、dnf（rpm）で入れたパッケージ。それぞれバージョンを表示する
    - 対象外: パッケージ管理の外で個別にビルド・配置したもの、pip などの言語ごとのパッケージ管理で入れたもの
    - 表示されないことを「未インストール」と扱わない。画面や出力にもその旨を明示する（例: Apache は表示されたが、個別に入れた Node.js は出ない）
  - 実際に使われているか（例: Java が動いているか）も分かるとよい
  - イメージ: FastAPI などの画面にアクセスすると、そのマシンの構成情報を一望できる

### 3.3 方式の候補

- 「あるべき状態」の定義を1つ持ち、適用・診断・監視を同じ定義から出す
- ゲスト内で実行する冪等なコマンドにする（何度流しても同じ結果、新規にも既存にも使える）
- ハイパーバイザ側の仕組みには頼らない
- アーキテクチャに依存しない（aarch64 と x86_64 の両方）
- 検知や設定の仕組みは既存OSSに乗り、自分で書くのは判断と見せ方に絞る
