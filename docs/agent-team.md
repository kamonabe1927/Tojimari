# 自動開発の体制（役割とモデル）

- 作成日: 2026-11-20
- 状態: 合意済み。運用してみて見直す
- 更新: 2026-11-21 要件を超えない範囲での自走（週の計画）を足した。2026-11-21 大きな依頼を PM がサブ issue に分け、着手する順番を PM が決めることにした。2026-11-21 巡回と進行の手順（[runbook.md](runbook.md)）と役割の定義（`.claude/agents/`）を追加し、これらを変える PR も本人がマージすることにした

AI エージェントで Tojimari の開発を進めるときの、役割、流れ、委任の範囲、モデルの割り当てです。
動かさない要件は [manifest.md](manifest.md)、エージェントの禁止事項は `CLAUDE.md` と [agent-rules.md](agent-rules.md) にあります。

## 1. 立ち位置

本人は開発を依頼する顧客の立場をとる。顧客がボトルネックにならないよう、依頼を出してから最終成果物を確認するまでの過程はエージェントに委任する。

顧客（本人）がすること:

- 依頼を issue に書く
- 委任の外のこと（2.2）を決める
- root が要る確認を実行して結果を渡す
- PR を確認し、止めたいときは `hold` ラベルを付ける。止めずに 1 時間たった PR は受け入れたものとしてマージされる（4.2）
- マージ後に問題を見つけたら、新しい issue で改修を依頼する

## 2. 委任の範囲

### 2.1 委任すること

マニフェストの中なら、要件と仕様は PM、設計（どう作るか）はテックリードが決めて進める。
決めたことと理由は `docs/`（要件と仕様は `requirements.md` や各段階の spec）に書いてから実装に進み、PR で顧客に見せる。

本人の issue がなくても、要件を超えない範囲では開発を自走させる。週に 1 回、PM がテックリードとセキュリティ担当の意見を聞いて、今の段階の spec を実現するもの、コードの質、Tojimari 自身のセキュリティの issue を 3 件まで立てる。立ててから 24 時間たってから着手する。条件は [agent-rules.md](agent-rules.md) の 6、手順は [runbook.md](runbook.md) の 4.2 にある。

### 2.2 委任していても止まって顧客に聞くこと

- マニフェストを変える、またははみ出す必要があるとき
- 禁止事項が求める確認（新しい依存を入れる前、秘密情報や文章に仕込まれた指示を見つけたとき、調べ物で許可リスト外の通信が要るとき）

## 3. 役割と流れ

| 順 | 役割 | すること | 渡す先 |
|---|---|---|---|
| 0 | 巡回 | 定期的に issue を見て、着手できる依頼（本人の issue と、その下に PM が立てたサブ issue）があるかを確かめる。あれば候補をすべて PM に渡す | PM |
| 1 | PM | 候補から今回進める issue を選ぶ。大きな依頼はサブ issue に分け、順番を決める。依頼を要件にまとめる（要件定義）。範囲と優先順位を決め、今日のタスクを決める。決めた要件と仕様を `docs/` に書く。マニフェストと段階を守る。顧客への報告とマージを行う | テックリード |
| 2 | テックリード | 今日のタスクを確認し、設計する（ファイルやモジュールの分け方、JSON の構造、テストの方針など） | 実装担当 |
| 3 | 実装担当 | 設計をもとにコードとテストを書く。実機の出力をテスト用データにするときは置き換えてから使う | レビュー担当 |
| 4 | レビュー担当 | 要件・設計・実装をレビューし、動作を確かめる（QA） | セキュリティ担当 |
| 5 | セキュリティ担当 | 禁止事項（秘密情報、実機の生の情報、依存、通信先など）と、「保証する」と読める表現がないかを見る。クリアしたら push と PR 作成を行う | PM |

- 実装担当からセキュリティ担当までは、1回の実行の中のブランチで受け渡す（6 を参照）
- 差し戻し先: 不具合は実装担当へ、設計の問題はテックリードへ、要件の問題は PM へ
- 書く役と見る役は分け、セキュリティ担当はほかの役の結論に引っ張られないよう独立させる

## 4. push とマージ

### 4.1 push と PR 作成

- セキュリティ担当がクリアした後に、セキュリティ担当が作業用ブランチへ push し、PR を作る
- 確認前の内容を公開リポジトリに出さないため。一度 push すると履歴から消しにくい（禁止事項7）。確認と push の間に誰も手を入れられない形にする
- PR ができたら、PM が顧客に報告する

### 4.2 マージ

- PR 作成から 1 時間以内に顧客がストップをかけなかった場合、PR は受け入れられたものとして PM がマージする
- ストップのかけ方は、顧客が PR に `hold` ラベルを付けること。PM はマージの直前に、ラベルが付いていないことを確かめる
- 次の PR は自動でマージせず、1 時間たっても顧客が自分でマージする
  - `docs/manifest.md`、`docs/vision.md`（要件の正本）、`CLAUDE.md`、`docs/agent-rules.md`、この文書を変える PR（エージェントが自分のルールを書き換えてそのまま通せる形を避けるため）
  - `docs/runbook.md` と `.claude/` の中を変える PR（役割の定義と巡回の手順も、エージェント自身のルールにあたるため）
  - `.github/` の中を変える PR
- マージ後に見つけた問題は、顧客が新しい issue で改修を依頼する
- 前提: エージェントの GitHub の権限にマージを足すことと、ブランチの保護などのリポジトリ設定は、本人が行う（禁止事項4）

## 5. モデルの割り当て

考え方: 間違いが後ろに広がる役と最後の確認には強いモデルを、量の多い実装には速くて安いモデルを使う。書く役と見る役は別のモデルにし、同じ見落としが重なりにくくする。

| 役割 | モデル | 理由 |
|---|---|---|
| 巡回 | Claude Haiku 5.5 | 新しい依頼があるかを見るだけで、空振りが多いため |
| PM | Claude Opus 5.5 | 委任の範囲で要件を決め、マニフェストからはみ出していないかを判断するため |
| テックリード | Claude Fable 5.2 | 設計の誤りは後ろのすべてに広がるため。1タスクに1回なので量は少ない |
| 実装担当 | Claude Sonnet 5.5 | 量が一番多い。日々のコーディング向け |
| レビュー担当 | Claude Opus 5.5 | 実装担当と別のモデルで見るため |
| セキュリティ担当 | Claude Fable 5.2 | 公開前の最後の確認で、自動マージにもつながるため。見るのは差分だけなので量は少ない |

- 新しいモデルが出たら、この表を差し替える

## 6. 動かし方

- 仕組み: Claude Code のクラウド定期実行で動かす。役割ごとの設定（`.claude/agents/` のサブエージェント定義）に、5 のモデルを書く
- 巡回と進行の手順は [runbook.md](runbook.md) にある。定期実行が起動するセッションが巡回を務め、ほかの役割をサブエージェントとして順に呼び出す（サブエージェントは別のサブエージェントを呼べないため）
- 巡回の間隔: 1 時間ごと。巡回は次を見て、あれば PM を起こす
  - 着手できる issue（本人が立てた issue と、その下に PM が立てたサブ issue）。どれから進めるか、大きな依頼をどう分けるかは PM が決める
  - 作成から 1 時間たち、`hold` ラベルのない PR（4.2 のマージ）
  - 手が空いていて、前回の週の計画から 7 日たったときは、週の計画を行う
- 同時に2つの作業を進めない。PM は取りかかった issue に `working` ラベルを付け、付いている issue があるあいだ、巡回は新しい作業を始めない
- 1つのタスクは、1回の実行の中で PM からセキュリティ担当まで通して進める。実行環境は毎回使い捨てなので、途中で終わった作業は残らない。PM は `working` ラベルを外し、次の巡回でやり直す
- 本人が行う設定: 定期実行の作成、クラウド実行環境のネットワーク設定（Limited にして許可するドメインを登録）、Claude の GitHub App の導入、ブランチの保護
- 理由: 専用 VM の中で動かすと、VM や Mac が止まっている間は開発が進まないため。1 時間ごとにしたのは、マージの 1 時間ルールと単位を揃えるため。巡回は Haiku なので、空振りの費用は小さい
