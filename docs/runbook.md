## 1. 起動するセッションと役割の関係

- 定期実行が起動するセッションが「巡回」を務める（モデルは Claude Haiku 5.5。定期実行の設定で指定する）
- 巡回は、仕事があれば各役割を `.claude/agents/` のサブエージェントとして順に呼び出し、結果を次の役割へ渡す
  - サブエージェントはさらに別のサブエージェントを呼べないため、役割どうしの受け渡しは巡回のセッションが行う
  - 巡回は判断をしない。受け渡しと、決められた条件の確認だけを行う。判断が要ることは PM に任せる
- 役割とサブエージェントの対応

| 役割 | サブエージェント | モデル |
|---|---|---|
| PM | `pm` | Claude Opus 5.5 |
| テックリード | `tech-lead` | Claude Fable 5.2 |
| 実装担当 | `implementer` | Claude Sonnet 5.5 |
| レビュー担当 | `reviewer` | Claude Opus 5.5 |
| セキュリティ担当 | `security` | Claude Fable 5.2 |

- サブエージェントは必ず前景で呼び出し、結果が返るまで待つ。すべて終わるまでセッションを終えない
- 1 回の実行の時間の上限は 50 分。次の巡回と重ならないようにするため。上限に近づいたら、進行中の作業をやめて 5 の「途中で止めるとき」に従う

## 3. 巡回の手順

上から順に確かめ、最初に当てはまったものだけを行う。1 回の実行で進める作業は 1 つだけ。

### 3.1 前回の作業が残っていないか

- `working` ラベルの付いた open の issue を探す
- あれば、その issue に PM が残した最新の「着手」コメントの時刻を見る
  - 60 分以内なら、前回の実行がまだ動いている可能性がある。何もせずに終了する
  - 60 分を超えていれば、前回の実行は途中で終わったとみなす。`working` ラベルを外し、issue に「前回の作業が途中で終わったため、やり直します」とコメントしてから、3.3 でその issue を拾い直す

### 3.2 マージを待っている PR がないか

次をすべて満たす open の PR があれば、`pm` を「マージの確認」として呼び出す。1 回の実行でマージするのは 1 本まで。

- エージェントが作った PR である
- 作成から 1 時間以上たっている
- `hold` ラベルが付いていない

マージしてよいかの最終判断（[agent-team.md](agent-team.md) の 4.2 の除外に当たらないか、マージ直前に `hold` が付いていないか）は `pm` が行う。

本人の判断を待つ点があり、自動でマージさせたくない PR には、`pm` が自分で `hold` ラベルを付ける。マージの確認の条件はラベルで決まっていて、issue のコメントに書いただけでは次の回で見落とされうるため、ラベルで止める。

### 3.3 新しい依頼がないか

次をすべて満たす open の issue を、着手の候補として集める。

- 作業の対象にしてよい issue である（2）。サブ issue を分けた親の issue は、分けた後は候補にしない
- `hold` ラベルが付いていない
- 週の計画で立てた issue なら、立ててから 24 時間たっている
- `working` ラベルが付いていない
- その issue を閉じる open の PR がまだない
- エージェントが作った open の PR がほかにない（前の PR がマージか close されるまで、次の依頼に着手しない。前の依頼の変更がまだ main に入っていないうちに次を作り始めると、同じ土台を二重に作ったり、マージのときにぶつかったりするため）
- 最新のコメントが、エージェントから本人への質問のまま本人の返事を待っている状態ではない

候補があれば、`pm` を「着手する issue の選択」として呼び出し、候補の番号をすべて渡す。巡回は自分で選ばない。サブ issue がすべて閉じた親の issue があれば、それも一緒に渡す（`pm` が親を閉じる）。

- 候補が 1 つでも `pm` に選ばせる（分けるべき大きさかの判断も `pm` が行うため）
- `pm` が「分けた」と返したら、その回はそこで終了する（4.1）
- `pm` が 1 つ選んだら、その issue で 4.3 の流れに進む

### 3.4 週の計画の時期か

次をすべて満たすときは、4.2 の週の計画を行う。

- 3.3 で候補がなかった
- エージェントが作った open の PR がない
- 最後の「週の計画」の記録の issue（4.2）が立ってから 7 日以上たっている。記録がまだなければ、今回が最初の計画

### 3.5 何もないとき

GitHub に何も書き込まずに終了する。それが普通の回である。

## 4. 依頼を進める流れ

### 4.1 大きな依頼を分ける

- 選んだ issue が 1 回の実行（50 分）で終わらない大きさなら、`pm` はその回を分けることだけに使う
- `pm` は本人の issue の下にサブ issue を立て（GitHub のサブ issue の機能を使う）、各サブ issue に、やること、やらないこと、終わりの条件、先に終わっている必要があるサブ issue を書く。分け方と進める順番とその理由は、親の issue にコメントする
- サブ issue の中身は親の issue の範囲を出ない。範囲を足したくなったら、分ける前に親の issue で本人に聞く
- 本人が分け方に意見をコメントしたら、次の回で `pm` が見直す。本人は、進めてほしくないサブ issue に `hold` ラベルを付けて止められる
- すべてのサブ issue が閉じたら、`pm` が親の issue に結果をまとめてコメントし、親の issue を閉じる

### 4.2 週の計画

本人の issue がなくても、要件を超えない範囲で開発を進めるための計画。条件は `docs/agent-rules.md` の 6 の「週の計画の例外」にある。

| 順 | 呼び出すもの | 頼むこと | 返してもらうもの |
|---|---|---|---|
| 1 | `pm` | 計画の材料づくり | `docs/vision.md` の今の段階の到達点、マニフェスト、今の段階の spec と、main のコードを照らし合わせた、足りないものの一覧 |
| 2 | `tech-lead` | 週の計画での意見（1 の一覧を渡す） | コードの質（リファクタリング、テスト）の観点での意見と候補 |
| 3 | `security` | 週の計画での意見（main のコードを見てもらう。1、2 は渡さない） | Tojimari 自身のセキュリティの観点での意見と候補 |
| 4 | `pm` | 計画の決定（1〜3 を渡す） | 立てた issue の番号 |

- 4 で `pm` は、3 件までの issue を立てる。タイトルの頭に「[自走]」を付け、本文に種類、根拠にした文書の箇所、やること、やらないこと、終わりの条件を書く
- `pm` は、計画の記録として「週の計画 <日付（UTC）>」という issue を立て、材料、意見、決めたこと、立てた issue（なければ「今週は立てない」とその理由）を書いて、すぐに閉じる。3.4 はこの issue の日付で 7 日を数える
- 立てた issue は、24 時間たってから 3.3 の候補になる

### 4.3 1 つの issue を進める


| 順 | 呼び出すもの | 渡すもの | 返してもらうもの |
|---|---|---|---|
| 1 | `pm` | issue の番号 | 着手したか（止まる場合はその理由）、今回のタスク、`docs/` に書いた要件と仕様 |
| 2 | `tech-lead` | PM の結果 | 設計（`docs/` に書いたもの）、実装担当への指示 |
| 3 | `implementer` | 設計と指示 | 実装したこと、テストの結果 |
| 4 | `reviewer` | 1〜3 の結果 | 通すか差し戻すか、差し戻し先と理由 |
| 5 | `security` | 作業ブランチの名前 | 通すか止めるか。通したときは PR の URL |
| 6 | `pm` | 5 の結果 | 本人への報告を終えたか |

- 作業ブランチは、実行環境が指定するブランチを使う。指定がなければ `agent/issue-<番号>` とする。1〜4 はこのブランチにコミットするだけで、push はしない
- 差し戻し: レビュー担当が差し戻したら、差し戻し先（不具合は `implementer`、設計の問題は `tech-lead`、要件の問題は `pm`）から流れをやり直す。差し戻しは 1 回の実行で 2 回まで。超えたら 5 の「途中で止めるとき」に従う
- セキュリティ担当には、ほかの役割の結論や理由を渡さない（独立して見てもらうため）。渡すのはブランチの名前だけ
- セキュリティ担当が止めたときは push しない。PM が理由を issue にコメントして本人に聞く

## 5. 止まるとき

### 5.1 本人に聞くとき

[agent-team.md](agent-team.md) の 2.2 に当たるとき（マニフェストを変える・はみ出す必要がある、禁止事項が求める確認が要る）は、`pm` が issue に質問をコメントし、`working` ラベルを外して終了する。本人の返事が付いたら、次の巡回で 3.3 から拾い直す。

### 5.2 途中で止めるとき

時間の上限、差し戻しの上限などで進められなくなったときは、`pm` が issue に「どこまで進んだか、何で止まったか」をコメントし、`working` ラベルを外して終了する。作業ブランチは push しない（実行環境は使い捨てなので、次の回は最初からやり直す）。
